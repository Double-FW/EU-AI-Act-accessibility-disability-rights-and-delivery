# Adoption and GitHub setup

## Put the files in a repository

Suggested repository name: **EU-AI-Act-Accessibility-and-Governance**.

1. Download and extract the ZIP package.
2. Open the extracted `EU-AI-Act-Accessibility-and-Governance` folder. Its contents include `README.md`, `AGENTS.md`, `LICENSE`, `docs`, `templates`, `sources` and `examples`.
3. On GitHub, create a new empty repository owned by **Double-FW**, using the suggested name or your preferred name. Choose the visibility you intend. Do not add GitHub-generated README/licence files because the package already contains them.
4. Open the new repository's file-upload option and upload the **contents inside** the extracted folder, retaining the subfolders. The README and licence should be at repository root, not inside an extra wrapper folder.
5. Commit the files. Check that the README renders and its local links open the guides.
6. Set a short description such as: “Human-centred EU AI Act guidance, governance runbook and accessibility delivery methods for people and agents.” Appropriate topics include `accessibility`, `eu-ai-act`, `ai-governance`, `inclusive-design` and `disability-inclusion`.

The package itself does not establish that a remote repository has been created or published. No authentication details, confidential records or real participant data belong in the public knowledge base.

GitHub's own instructions cover [creating a repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository) and [uploading files and folders](https://docs.github.com/en/repositories/working-with-files/managing-files/adding-a-file-to-a-repository).

## Adopt the method in an organisation

1. Choose one priority use and name a service owner and competent decision functions. Confirm actual authority, resources and access.
2. Check current law, national/sector requirements, dates and standards status through WF01. Record the verified position.
3. Complete WF02's scope record and WF03's requirement plan. Include all relevant surfaces and people.
4. Adapt the policy starter and templates to existing organisational systems. Approve only the organisation's actual commitments; do not invent services or authority.
5. Pilot procurement, assessment, release, monitoring and complaint/incident processes on a bounded use. Collect real evidence and correct gaps.
6. Review outcomes, staff burden, evidence quality and affected people's experience. Adjust before broader adoption.

No software installation is required to read or use the documents. Workflow descriptions are human-readable procedures; they are not executable integrations.

## Maintain the knowledge base

Assign a maintainer, source reviewers and an update process. Use WF12 after legal/standards/source changes, preserving history and affected requirements. Suggested periodic reviews are local planning choices; no scheduled task is created by these files.

Keep live personal/commercial case evidence in authorised protected systems and link it by controlled references. Keep templates blank in the public repository. MIT permits commercial reuse of original repository material subject to its notice conditions; external sources retain their own terms.
